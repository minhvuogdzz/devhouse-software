## 20. SEO Architecture

(ADR-002, ADR-014)

### 20.1 Limits of a client-rendered Vite + React SPA

| Concern | Pure SPA behaviour | Impact |
|---|---|---|
| Initial HTML | An empty `<div id="root">` and script tags | Content is invisible until JavaScript runs |
| Google | Renders JavaScript, but in a deferred second pass with a render budget | Slower, less reliable indexing of new content |
| Social link previews (Facebook, LinkedIn, X, Zalo, Slack, Telegram) | Do **not** execute JavaScript | Every shared link shows the same generic title and image |
| AI and answer-engine crawlers | Most do not execute JavaScript | Services and articles are not ingested |
| Status codes | Server returns `200` for every path | Soft 404s; no real `301` for moved content |
| Core Web Vitals | LCP waits for JS download, parse, fetch and render | Worse LCP on mobile |

For a software company whose website is its primary sales and credibility channel, these are not acceptable. The stack itself is fine; the *rendering mode* is the problem.

### 20.2 Options

| Option | Fixes social/AI crawlers | Real status codes | Extra moving parts | Verdict |
|---|---|---|---|---|
| A. SPA + client-side head manager | No | No | None | Insufficient |
| B. SPA + server-side meta injection (server rewrites `<head>` per URL) | Metadata only; body still empty | Possible | Small | Acceptable minimum; fallback plan |
| C. SPA + bot-detection prerendering (headless browser) | Yes | Partially | Headless Chrome on the VPS, cache, user-agent sniffing; search engines describe this as a workaround | Rejected |
| D. Build-time static generation | Yes | Yes | Content change requires a rebuild and redeploy; conflicts with Admin-driven publishing | Rejected as the primary mode |
| **E. Server-side rendering with React Router framework mode** | **Yes** | **Yes** | One Node container instead of static files; hydration discipline | **Chosen** |
| F. Switch to Next.js or similar | Yes | Yes | Replaces Vite and React Router conventions | Rejected: unnecessary stack change |

Option E uses the libraries the brief already names. React Router's framework mode *is* a Vite plugin; routes gain `loader` and `meta` exports and the same components render on the server and hydrate in the browser.

**Trade-offs accepted:** `web` is a Node process (memory, a health check, restarts) rather than static files; components must be hydration-safe (no `window` access during render, no time- or random-dependent markup); the team must learn loaders. **Mitigations:** edge micro-caching makes most requests as cheap as static files and serves stale HTML if `web` or `api` is down; an ESLint rule and a hydration-warning check in E2E catch unsafe code.

**If the team rejects SSR:** implement option B plus a pre-launch commitment to revisit. The rest of this architecture (API, content model, admin, infra) is unaffected; only `apps/web` hosting changes.

### 20.3 Metadata

Each route module exports `meta({ data })` built by one helper, `buildSeo({ entity, page, site, url })`, applying a strict precedence:

```
entity.seo.*  →  derived from entity (title, excerpt, cover image)  →  page.seo.*  →  site default SEO  →  code defaults
```

Output per page: `<title>` (pattern `%s | Dev House Software`, configurable), meta description, canonical, `robots`, Open Graph (`og:title`, `og:description`, `og:image` 1200×630, `og:type`, `og:url`, `og:locale`), Twitter/X card (`summary_large_image`), and JSON-LD.

### 20.4 Structured data (JSON-LD)

| Page | Types |
|---|---|
| All | `Organization` (from site settings), `WebSite` |
| Any page below home | `BreadcrumbList` (same data as the visible breadcrumbs) |
| Service detail | `Service` with `provider`; `FAQPage` when FAQs exist |
| Project detail | `CreativeWork` / `Article` |
| Blog post | `BlogPosting` with `author`, `datePublished`, `dateModified`, `image` |
| Contact | `ContactPoint` within `Organization`; `LocalBusiness` if a physical office is published |
| Careers | `JobPosting` per role [Phase 2, when postings become a collection] |

JSON-LD is generated by typed builder functions and serialised safely (escaping `<`), never assembled from admin-entered markup.

### 20.5 Canonicals, pagination, filters

- One canonical host (`https://www.devhouse.example`); apex and `http` redirect with `301`.
- No trailing slash; Nginx normalises.
- Paginated lists: `?page=N` self-canonical; page 1 canonicalises to the bare URL.
- Filter and search combinations: `noindex, follow`, canonical to the unfiltered list. Category and tag landing pages get clean, indexable paths (`/blog/category/:slug`, `/blog/tag/:slug`).
- Tracking parameters are stripped from canonicals.
- Each language version is self-canonical and emits `hreflang` alternates for every locale the page exists in, plus `x-default` pointing at the Vietnamese URL (§30.6).

### 20.6 Sitemap, robots, redirects

| Artefact | Implementation |
|---|---|
| `/sitemap.xml` | Resource route in `web` that renders XML from `GET /api/v1/seo/sitemap` (static routes + every published item with `lastmod`). Cached 1 hour. Split into a sitemap index if it ever approaches 50,000 URLs. |
| `/robots.txt` | Resource route. Production: allow all, reference the sitemap. Any non-production environment: `Disallow: /` plus `X-Robots-Tag: noindex` at the edge. |
| Redirects | `redirects` collection. Created automatically when a published slug changes; manageable in Admin. The catch-all route resolves them before returning 404. Chains are flattened on write. |
| 404 | Real `404` status, `noindex`, helpful links. |

### 20.7 On-page requirements (enforced in review and by lint where possible)

One `<h1>` per page; ordered heading levels; semantic landmarks (`header`, `nav`, `main`, `footer`, `article`, `section`); real `<a href>` for all navigation; descriptive link text; alt text required in the media library with an explicit "decorative" option; slugs lowercase, hyphenated, ASCII (Vietnamese titles are transliterated: "Phát triển ứng dụng" → `phat-trien-ung-dung`).

## 21. Performance Architecture

### 21.1 Targets

Practical objectives measured at the 75th percentile on mobile, not guarantees.

| Metric | Target |
|---|---|
| LCP | ≤ 2.5 s |
| INP | ≤ 200 ms |
| CLS | ≤ 0.1 |
| TTFB, edge-cached HTML | ≤ 200 ms |
| TTFB, uncached SSR | ≤ 600 ms |
| Lighthouse (mobile, public pages) | Performance ≥ 90, Accessibility ≥ 95, Best Practices ≥ 95, SEO ≥ 95 |
| Web JS for first route | ≤ 170 kB gzip total; no route chunk above 60 kB gzip |
| Web CSS | ≤ 30 kB gzip |
| Admin entry JS | ≤ 350 kB gzip (rich-text editor lazy-loaded separately) |
| API p95, public GET (server time) | ≤ 200 ms uncached, ≤ 20 ms cached |
| API p95, admin write | ≤ 500 ms |
| Database | No collection scans on public endpoints; p95 query ≤ 50 ms |
| 5xx rate | < 0.5 % of requests, rolling 7 days |
| Availability objective | 99.5 % monthly on a single VPS (about 3.6 h/month), excluding announced maintenance |

Budgets are enforced by Lighthouse CI and a bundle-size check in the pipeline **[Recommended]**; a breach fails the merge request.

### 21.2 Frontend

| Technique | Application |
|---|---|
| Server rendering | Content and LCP image are in the first HTML response |
| Route-level code splitting | Automatic per route module in `web`; `lazy()` per feature route in `admin` |
| Component lazy loading | Only for heavy, below-the-fold or interaction-gated pieces (rich-text editor, gallery lightbox, charts). Not for ordinary components: over-splitting hurts. |
| Bundle hygiene | Named imports, no barrel files re-exporting whole features, bundle visualiser run in CI on demand, dependency additions reviewed for size |
| Server state | TanStack Query with sensible `staleTime` prevents refetch storms; link prefetch on hover/viewport for likely next pages |
| Re-renders | Server state stays out of React context; URL state for filters; memoisation only where profiling shows a problem |
| Images | Cloudinary `f_auto,q_auto`, fixed-ladder `srcset` + `sizes`, explicit dimensions, lazy by default, `fetchpriority="high"` + preload for the LCP image |
| Fonts | Self-hosted WOFF2, at most two families, subset to Latin + Vietnamese, `font-display: swap`, preload the primary text face, metric-matched fallback to avoid layout shift |
| Third parties | `preconnect` to `res.cloudinary.com` only; analytics loaded after interaction/idle; no third-party script in the critical path |
| Animation | CSS transforms/opacity; honour `prefers-reduced-motion`; no layout-thrashing scroll handlers |

### 21.3 Backend

- Indexes for every public query (§11.4, §39); `.lean()` and projections; separate list and detail DTOs so list responses stay small.
- Batched reference resolution: one `$in` query per referenced collection per request, never one query per item.
- Counts for pagination are cached with the list; deep pages are capped (§26).
- Aggregations only where needed (dashboard counts, tag counts) and cached.
- In-process cache for resolved singletons and hot lists (§25).
- Response compression at the edge, not in the API.
- Connection pooling and timeouts set explicitly; no unbounded queries (`limit` always applied).

### 21.4 Nginx

HTTP/2 enabled; HTTP/3 **[Optional]** once verified on the VPS image. Brotli where the module is available, gzip otherwise, for text types only. `immutable` one-year caching for hashed assets. Micro-cache for HTML and public API GETs with stale-while-revalidate and stale-if-error. Keep-alive to upstreams. Details in §33.

## 22. Responsive Architecture

One codebase, fluid layout, mobile-first.

| Principle | Implementation |
|---|---|
| Breakpoints | Tailwind defaults (`sm` 640, `md` 768, `lg` 1024, `xl` 1280, `2xl` 1536) plus one `3xl` (1920) for very large displays. Layouts are designed to be correct *between* breakpoints, not only at them. |
| Small mobile | Minimum supported width 320 px. No horizontal scroll at any width. |
| Containers | Centred, max-width capped (~1280–1440 px) with fluid side padding; on very large displays content stays readable and backgrounds extend full-bleed. |
| Fluid type and spacing | `clamp()`-based scale defined as theme tokens, so headings and section spacing grow smoothly without per-breakpoint overrides. |
| Grids | CSS grid with `auto-fit`/`minmax` for card lists; column counts emerge from available width. |
| Component-level responsiveness | Container queries for cards and sections reused in different column widths. |
| Images | `srcset`/`sizes` matching the layout; `aspect-ratio` reserved. |
| Navigation | Desktop: horizontal with accessible dropdowns. Mobile: full-height drawer built on a dialog primitive (focus trap, scroll lock, `Esc`, restore focus). Same data source. |
| Touch | Targets at least 44×44 px with spacing; no hover-only interactions. |
| Forms | Single column on mobile; correct `type`, `inputmode`, `autocomplete`; 16 px minimum input font size to prevent iOS zoom. |
| Tables | Public: avoid; use cards. Admin: priority columns stay, secondary columns collapse into an expandable row, horizontal scroll with a sticky first column as the last resort. |
| Admin | Collapsible sidebar (drawer below `lg`), responsive forms, usable on a tablet. Phone support is best-effort for triage tasks (reading contact requests). |
| Verification | Playwright viewport matrix (360, 768, 1280, 1920) for key pages; manual checks on real iOS and Android devices before launch. |

## 23. Accessibility

**Target: WCAG 2.2 Level AA** for the public site, and for the admin's core flows.

**Why AA:** it is the level referenced by most legislation and procurement standards, it covers the barriers that affect real users (contrast, keyboard, forms, focus), and it is achievable without constraining design. AAA is not adopted as a blanket target because several criteria are impractical site-wide; individual AAA practices are adopted where cheap (for example, 7:1 contrast for body text).

| Area | Requirement |
|---|---|
| Semantics | Landmarks, one `h1`, ordered headings, lists as lists, buttons as `<button>`, links as `<a>` |
| Keyboard | Everything operable by keyboard; logical tab order; no traps; skip-to-content link |
| Focus | Visible `:focus-visible` ring with ≥ 3:1 contrast; focus not obscured by sticky headers (2.2); focus moved to the main heading after client navigation and the route announced via a live region |
| Forms | Programmatic labels; required state conveyed; errors in text, linked with `aria-describedby`, announced, and focus moved to the first invalid field; no placeholder-only labels |
| ARIA | Native elements first. ARIA only for custom widgets, supplied by audited primitives (Radix / React Aria) |
| Dialogs and menus | Focus trap, `Esc` to close, focus restoration, inert background, labelled |
| Colour | Text ≥ 4.5:1, large text and UI components ≥ 3:1, **in both the light and the dark theme**; information never conveyed by colour alone; tokens checked when the palette is defined |
| Motion | `prefers-reduced-motion` disables non-essential animation; no auto-playing motion longer than 5 s without a control |
| Targets | ≥ 24×24 px minimum (2.2), 44×44 px design default |
| Media | Alt text enforced by the media library; captions/transcripts when video is introduced |
| Zoom and reflow | Usable at 200 % zoom and 320 px width without loss of content |
| Language | `lang` on `<html>`, and on inline passages in another language |
| Rich text | Editor enforces heading order below the page title and requires alt on images |

Verification: `eslint-plugin-jsx-a11y` in CI; axe checks inside Playwright runs for key pages **[Recommended]**; a manual keyboard and screen-reader pass (VoiceOver, NVDA) before launch and after major UI changes. Automated tools find roughly a third of issues, so the manual pass is not optional.

## 24. Security Architecture

### 24.1 Controls by layer

| Layer | Controls |
|---|---|
| **Transport** | TLS 1.2+ at the edge, HSTS (preload after a trial period), HTTP → HTTPS redirect, modern cipher configuration |
| **Edge (Nginx)** | Host allow-list (unknown hosts dropped), rate limiting, body size limits, admin API not routed on `www`, security headers, `server_tokens off`, dotfile and source-map blocking |
| **Browser policy** | CSP, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `frame-ancestors 'none'`, `Permissions-Policy` minimal |
| **API** | Helmet, origin check, strict JSON parsing with size limits, Zod validation, session auth, RBAC, generic errors, per-route rate limits |
| **Data** | Mongoose strict schemas, `sanitizeFilter`, no raw query objects from input, least-privilege DB users, Atlas IP allow-list, encryption at rest (Atlas) |
| **Secrets** | Environment only, never in Git or images, never in logs; rotation runbook |
| **Supply chain** | Lockfile, immutable installs, audit and container scan in CI, pinned base images, automated update MRs |
| **Runtime** | Non-root containers, read-only filesystem, dropped capabilities, only the edge publishes ports, host firewall, SSH keys only |
| **Process** | Protected branches, reviewed merge requests, protected CI variables, audit log |

### 24.2 Content Security Policy

Generated per response by the `web` server (it knows the nonce) and by Nginx for the static admin.

```
default-src 'self';
script-src 'self' 'nonce-<per-response>';
style-src 'self';
img-src 'self' data: https://res.cloudinary.com;
font-src 'self';
connect-src 'self' https://api.cloudinary.com;          (admin only: direct upload)
frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none';
```

- Analytics and CAPTCHA domains are appended only when those features are enabled in settings.
- Roll out as `Content-Security-Policy-Report-Only` first, then enforce.
- Edge-cached HTML reuses its nonce for the cache lifetime (≤ 60 s). This is an accepted trade-off for public, non-personalised pages; the admin never has cached HTML with inline scripts.

### 24.3 CORS

Not enabled. All browser calls are same-origin. The API still rejects state-changing requests whose `Origin` is not an allowed site origin. If a third-party client is added later, CORS is enabled only for a dedicated `api.` host with an explicit origin allow-list and never with credentials + wildcard.

### 24.4 Input handling

- **Validation** at the boundary with Zod: type, length, format, enum. Unknown keys stripped.
- **XSS:** React escapes output; rich text is typed JSON rendered through a whitelist; no HTML is stored or injected; link schemes validated; JSON-LD serialised safely; CSP as defence in depth.
- **NoSQL injection:** Express 5's simple query parser yields strings, not objects; schemas require primitives; Mongoose `sanitizeFilter` and `strictQuery` enabled; filters are built from whitelisted fields only (§26).
- **Mass assignment:** DTO whitelisting on input; server-owned fields (`createdBy`, `status` transitions, `roles`) are set only by services.
- **Uploads:** §18.

### 24.5 Threat model

| Threat | Impact | Mitigation | Residual risk |
|---|---|---|---|
| Credential theft (phishing, reuse) | Admin takeover, content defacement, data access | Argon2id, strong-password policy, lockout, session listing/revocation, audit, MFA in Phase 2, optional IP restriction on the admin host | Until MFA ships, a phished password is sufficient. **Medium** → Low after MFA. |
| Brute-force / credential stuffing | Account compromise, lockout abuse | Edge + app rate limits per IP and per account, progressive lockout, generic errors | Distributed slow attacks; attacker can lock a known account (admin can unlock). Low. |
| Session theft | Impersonation | HttpOnly, Secure, SameSite=Strict, host-only cookie; token hashed at rest; short idle timeout; revocation; CSP | Malware on the admin's device. Low. |
| XSS (stored or reflected) | Session riding, defacement | No stored HTML, React escaping, whitelist renderer, scheme validation, CSP with nonces, admin on a separate origin | Vulnerable third-party script or a React escape hatch introduced later. Low. |
| CSRF | Unwanted admin actions | SameSite=Strict, origin check, JSON-only bodies, no CORS | Negligible in modern browsers. |
| NoSQL injection | Data exposure, auth bypass | Typed schemas, simple query parser, `sanitizeFilter`, whitelisted filters | Low. |
| Malicious file upload | Malware delivery to staff, stored XSS via SVG/HTML | Admin uploads signed with format allow-list; visitor uploads proxied, magic-byte checked, size-limited, stored private, forced download, SVG/HTML refused | No malware scan in MVP: a malicious but well-formed PDF/Office file could reach an admin. **Medium** until scanning is added. |
| SSRF | Internal network access | The API never fetches a user-supplied URL. Cloudinary "upload by URL" and fetch delivery are not used and should be disabled in the account. | Reintroduced if a link-preview or import feature is added; must then use an allow-list. Low. |
| CORS misconfiguration | Cross-origin data access | CORS is off; same-origin design | Low. |
| Privilege escalation | Editor becomes admin | Backend RBAC on every admin route (test-enforced), subset rule for role assignment, self-modification blocked, session invalidation on role change | Logic bug in a new module; mitigated by the route-coverage test and review. Low. |
| Broken access control (IDOR, draft leakage) | Unpublished content or contact data exposed | Separate public and admin route files and DTOs; published scope in the repository; admin API unroutable from `www` | Low. |
| Rate-limit abuse / DoS | Unavailability, cost | Nginx limits, micro-cache absorbs read floods, pagination caps, body limits; optional CDN/WAF in front | A volumetric attack exceeds a single VPS. **Medium** without a CDN/WAF. |
| Contact spam | Polluted inbox, wasted time | Honeypot, minimum fill time, rate limit, link heuristics, spam status, optional CAPTCHA | Targeted human spam. Low. |
| Secret leakage | Database or media account compromise | No secrets in Git/images/frontends, secret detection in CI, protected + masked variables, env files `0600` on the VPS, log redaction, rotation runbook | Developer machine compromise. Low–Medium. |
| Supply-chain compromise | Malicious code in the build | Lockfile + immutable install, install scripts disabled except an allow-list, audit and image scan in CI, pinned base images, reviewed update MRs, minimal dependencies | Zero-day in a trusted package. Medium (industry-wide). |
| Misconfigured Nginx | Exposed internals, header bypass, open proxy | Config in Git, reviewed, `nginx -t` in CI, default server drops unknown hosts, correct real-IP handling, no directory listing | Low. |
| Container escape / image CVEs | Host compromise | Non-root, read-only FS, `cap_drop: ALL`, `no-new-privileges`, no Docker socket mounted, regular base image rebuilds, image scanning | The deploy user's Docker access is root-equivalent on the host. Low–Medium; mitigated by a forced-command SSH key (§37). |
| Cloudinary transformation abuse | Quota exhaustion, cost | Fixed width ladder, Strict Transformations, usage alerts | Low once strict mode is on. |
| PII exposure (contact requests) | Privacy/legal harm | RBAC, private attachments, minimal fields, retention policy, IP stored only as needed, access audited | Low. |

### 24.6 Operational security

- VPS: firewall allowing 22 (optionally restricted or moved behind a VPN), 80, 443; SSH key-only, no root login; fail2ban; unattended security updates; Docker log rotation. Docker bypasses host firewalls for published ports, so only `edge` publishes any.
- Dependency updates: automated merge requests weekly, security updates immediately.
- Incident basics in `docs/security/`: how to revoke all sessions, rotate each secret, restore from backup, and roll back a release.

## 25. Caching Architecture

(ADR-015)

### 25.1 Layers

| Layer | What | TTL | Invalidation |
|---|---|---|---|
| **Browser + CDN-style headers** | Hashed JS/CSS/fonts | 1 year, `immutable` | New filename per build |
| **Cloudinary CDN** | Images | Long | New `public_id`, or explicit invalidation on replace |
| **Nginx micro-cache** | Public HTML from `web`; public `GET /api/v1/*` on `www` | 60 s, `stale-while-revalidate` 5 min, `stale-if-error` 1 h | Time-based only |
| **API in-process cache** (`lru-cache`) | Resolved settings, navigation, page content; hot public lists; session lookups | 5 min content / 30 s sessions, bounded size | **Explicit, by tag, on every admin write** |
| **TanStack Query (web)** | API data in the browser | `staleTime` 5 min, `gcTime` 30 min | Time-based; focus refetch off for content |
| **TanStack Query (admin)** | Admin data | `staleTime` 0–30 s | Invalidated by mutations |
| **Redis** | — | — | [Future] |

### 25.2 Policy per content type

| Content | API response header | Edge | Notes |
|---|---|---|---|
| Site bootstrap (settings + navigation) | `public, max-age=60, stale-while-revalidate=300` | 60 s | Hottest call; in-process cached |
| Page content | same | 60 s | |
| Services, solutions, technologies | same | 60 s | |
| Projects, blog lists and details | same | 60 s | Scheduled items appear when caches roll |
| Search / filtered lists | `public, max-age=30` | 30 s, keyed by full query string | Query params normalised and bounded to limit key cardinality |
| Sitemap | `public, max-age=3600` | 1 h | |
| HTML (public) | `public, max-age=0, s-maxage=60, stale-while-revalidate=300` | 60 s | Browser always revalidates; edge absorbs load |
| Admin API, auth | `no-store` | Bypassed | |
| Contact POST | `no-store` | Bypassed | |

### 25.3 Staleness budget

Because SSR loaders call the API over the internal network (not through Nginx) and the API invalidates its in-process cache on write, layers do not stack. The maximum delay between an admin save and the public site is **one edge TTL: about 60 seconds**.

### 25.4 Why this is enough, and when Redis arrives

- A 60-second micro-cache turns any traffic spike on a page into one upstream render per minute.
- `stale-if-error` keeps the public site serving during an API or `web` restart, which also hides deploy blips.
- Nginx open-source has no selective purge; a short TTL makes one unnecessary.
- **Redis trigger:** a second API replica (shared invalidation and rate-limit counters), a real job queue, or measured session-lookup pressure. The `core/cache` interface is written so the backing store can change without touching services.

## 26. Search / Filtering / Pagination

### 26.1 One list-query pattern

Every list endpoint uses the same pipeline:

```
raw query string
  → Zod list schema for that resource      (types, bounds, enums, defaults)
  → buildListQuery(valid, resourceConfig)  → { filter, sort, skip, limit }
  → repository.paginate(...)               → { items, total }
```

Each resource declares a small config; nothing from the request reaches MongoDB unless it is named here:

```js
// concept
export const projectListConfig = {
  filters: { category: 'category', service: 'services', technology: 'technologies', featured: 'isFeatured' },
  sortable: ['publishedAt', 'title', 'sortOrder'],
  defaultSort: '-publishedAt',
  search: 'text',
  maxLimit: 50,
};
```

### 26.2 Parameters

| Parameter | Rule |
|---|---|
| `page` | Integer ≥ 1, default 1; public lists capped (e.g. page × limit ≤ 2,000) |
| `limit` | Default 12 (public) / 20 (admin); max 50 (public) / 100 (admin) |
| `sort` | One whitelisted field, `-` prefix for descending; a stable tiebreaker (`_id`) is always appended |
| `search` | Trimmed, 2–100 characters |
| Filters | Whitelisted names only; public filters take **slugs** (resolved to ids server-side), admin filters take ids |
| `status` | Admin only. Public lists are always "published and due". |
| `fields` | Not offered publicly; list vs detail DTOs cover the need. [Optional] whitelisted `fields` on admin export endpoints. |

### 26.3 Pagination strategy and its limits

| Strategy | Used for | Limits |
|---|---|---|
| **Offset (`page`/`limit`)** | Public lists and admin tables, where page numbers and totals are useful and collections are small (hundreds to low thousands) | `skip` cost grows with depth; `countDocuments` on every request; items can shift between pages if content is published mid-browse. Mitigated by depth caps, cached counts and stable sort. |
| **Cursor (keyset)** | `audit_logs`, `contact_requests` (append-heavy, can grow large) | No page jumping or total count; cursor is an opaque encoding of `(createdAt, _id)` |

If a public collection ever exceeds roughly 10,000 items, switch that list to keyset pagination; the response contract already supports both shapes.

### 26.4 Search

| Stage | Mechanism | Notes |
|---|---|---|
| **MVP** | MongoDB `$text` index per collection with field weights, sorted by text score | Whole-word matching, no typo tolerance, no prefix match. `default_language: 'none'` for mixed Vietnamese/English content. |
| Admin quick-filter | Anchored, escaped, case-insensitive prefix match on `name`/`title` | Never an unanchored regex from user input |
| **Phase 2** | **Atlas Search** (managed, Lucene-based) behind the same `repository.search()` method | Relevance, autocomplete, fuzzy matching, language analysers, cross-collection site search. No new infrastructure to operate. |
| Not planned | Elasticsearch / OpenSearch | No requirement justifies a separate cluster. |

### 26.5 Preventing inefficient queries

Whitelisted filters only; every filter + sort combination maps to an index; `limit` is mandatory; regex is anchored and escaped; `explain()` assertions for the main public queries in integration tests **[Recommended]**; slow-query logging in the repository layer above a threshold (e.g. 200 ms).

## 27. Logging / Monitoring

### 27.1 Structured logging

- `pino` JSON to stdout in `api` and `web`; Nginx access log in JSON. Docker captures stdout with rotation (`max-size`, `max-file`).
- Every line carries: `time`, `level`, `service`, `env`, `version` (image tag), `requestId`, and where applicable `userId`, `route`, `status`, `durationMs`.
- **Request ID:** Nginx generates `$request_id`, sends it upstream as `X-Request-Id`, the API and web server adopt it, return it in the response header and in `meta.requestId`, and forward it on internal calls. One id traces a page view from edge to database.
- **Redaction:** `authorization`, `cookie`, `set-cookie`, passwords, tokens, signatures and contact message bodies are redacted by the logger configuration. Request bodies are not logged by default.
- Levels: `info` in production, `debug` in development; expected 4xx at `info`/`warn`, 5xx at `error` with stack.

### 27.2 What is watched

| Signal | Source | Action |
|---|---|---|
| Application errors | Error tracker (web, admin, api) with release tagging and source maps uploaded privately | Alert on new issue types and on spikes |
| API latency and status | Request logs (`durationMs`, `status`) | Weekly review in MVP; dashboards in Phase 2 |
| Database failures | Mongoose connection events, readiness check, Atlas alerts (connections, replication, disk) | Alert |
| Slow queries | Repository timing log + Atlas Performance Advisor | Index or query fix |
| Authentication failures | Audit log + `warn` logs | Alert on bursts |
| Deployment outcome | GitLab environments + post-deploy health gate | Automatic rollback, pipeline failure notification |
| Uptime | External monitor (hosted, or self-hosted on a *different* machine) probing the home page and `/api/v1/health` every minute | Alert to the team channel |
| Host | Disk, memory, CPU, certificate expiry | Simple alerts (provider monitoring or a lightweight agent) |

### 27.3 Tooling recommendation

| Tool | Tag | Reason |
|---|---|---|
| External uptime monitor | [Required] | The only way to learn the site is down when the VPS itself is down |
| Error tracker | [Recommended] | Frontend errors are otherwise invisible |
| Atlas built-in alerts | [Required] | Already included |
| Log aggregation (Loki/Grafana or a hosted service) | [Phase 2] | `docker logs` + `jq` is adequate for one host at launch |
| Metrics (Prometheus) and tracing (OpenTelemetry) | [Future] | Valuable once there are multiple services or performance work that logs cannot answer |

### 27.4 Audit logs

Separate from application logs: business-level, stored in MongoDB, visible in Admin.

- Written by the **service layer** after a successful state change through `audit.record()`, which reads actor, IP and request ID from the request context.
- Captured: `actor { id, email, roleKeys }`, `action` (`service.create`, `project.update`, `blog.publish`, `media.delete`, `navigation.update`, `user.roles.update`, `settings.update`, `auth.login.failure`, …), `resource { type, id, label }`, `changes` (names of changed fields; before/after values only for a whitelist of non-sensitive fields such as `status`, `slug`, role keys), `requestId`, `ip`, `userAgent`, `outcome`, `createdAt`.
- Never captured: passwords, tokens, cookies, full contact messages, secrets.
- Append-only: no update or delete endpoint exists. Retention through an optional TTL index (suggested 24 months).
- An audit write failure is logged as an error but does not fail the user's operation in MVP. If strict guarantees are later required for specific actions, wrap them in a transaction.

## 28. Health Checks

| Endpoint | Purpose | Checks | Response |
|---|---|---|---|
| `GET /api/v1/health/live` | Container liveness | Process responds | `200` always if the event loop is alive |
| `GET /api/v1/health/ready` | Readiness and deploy gate | MongoDB ping with a 2 s timeout; configuration loaded | `200` when ready, `503` otherwise |
| `GET /api/v1/health` | External monitors | Same as ready, summarised | `200 { status: "ok" }` or `503 { status: "degraded" }` |
| `GET /healthz` on `web` | Liveness for the SSR container | Process responds (does not call the API, so an API outage does not restart `web`) | `200` |
| `GET /healthz` on `admin` and `edge` | Liveness | Nginx responds | `200` |

- Public health responses expose **no** versions, hostnames or dependency details. A detailed variant (dependency latencies, version, uptime) is returned only on the internal network.
- Cloudinary and SMTP are *not* part of readiness: their outage must not take the site out of rotation. Their status appears in the detailed variant only.
- Docker `HEALTHCHECK` uses the liveness endpoints; the deploy script waits on readiness (§37).

## 30. Internationalization

Vietnamese and English are both first-class from the first release (project rule P2, ADR-016).

### 30.1 Rules

- Locales: `vi` (default) and `en`, defined once in `@devhouse/shared/locales.js` (`LOCALES`, `DEFAULT_LOCALE`).
- **The URL alone decides the language.** No redirect by `Accept-Language`, cookie or IP. This keeps pages cacheable per URL and predictable for crawlers.
- A **language switch in the header** links to the same page in the other language.
- **A page never mixes languages.** There is no fallback from one language to the other.
- **No user-visible string is hardcoded** in a component, in either app.

### 30.2 URL strategy

| Locale | Pattern | Example |
|---|---|---|
| `vi` (default) | Unprefixed | `/services/phat-trien-web` |
| `en` | `/en` prefix | `/en/services/web-development` |

- Route segments (`services`, `projects`, `blog`, …) are the same in both languages, so there is one route table. Item **slugs are localized** for services, solutions, projects and blog posts.
- All internal links are built with `localePath(path, locale)`; menu items and CTAs store unprefixed paths.
- Switch target: for fixed pages, add or remove the prefix. For detail pages, the API returns `alternates` (`{ vi: '/services/…', en: '/en/services/…' }`) containing only the locales the item exists in; when the item does not exist in the other language, the switch goes to that language's list page.
- Alternatives rejected: both locales prefixed (forces a redirect on `/`), per-language subdomains or domains (split authority, extra certificates and cookies), translated route segments (two route tables for little gain).

### 30.3 Three kinds of text

| Kind | Examples | Mechanism |
|---|---|---|
| UI chrome | Buttons, labels, form errors, pagination, empty states | Per-app dictionaries `locales/vi.js` and `locales/en.js`, read through `t(key, params)`. A unit test asserts both dictionaries have identical keys. |
| Singleton content | Page sections, site settings, navigation labels | Localized leaves `{ vi, en }` in code defaults and in database overrides; resolved per leaf, then one language is picked (§13.6). Defaults exist in both languages. |
| Collection content | Services, solutions, projects, posts, categories, tags, authors | `LocalizedString` / `LocalizedRichText` fields on the document (§30.4) |

### 30.4 Collection content model

- `LocalizedString = { vi*: String, en: String }`. The default-locale value is required; English is optional.
- **Localized:** names and titles, descriptions, rich text, text inside repeaters (features, FAQs, results), SEO text, alt text, and the slug of services, solutions, projects and posts.
- **Shared across languages:** relations, images, icons, flags, dates, ordering, URLs, status. Repeater arrays have one structure with localized text inside each item, so the two languages cannot drift in shape.
- **Availability:** each document has a derived `locales: [String]` array, recomputed on save. A locale is included when every field required for it is filled (name/title, short description, slug; for posts also content). Public queries filter on `locales: <locale>`, so an untranslated item simply does not appear in that language.
- Optional fields missing in a language are omitted in that language, never borrowed from the other.
- Publishing state is per document, not per language. English appears as soon as it is complete on a published item.
- Admin forms show the two languages side by side per field, with a per-language completeness indicator on the form and in list screens.
- Proper nouns (technology names, client names) are plain strings.
- Search: one text index per collection covering both languages' subfields.

Alternatives rejected: one document per language (duplicates relations and images, complicates ordering and publishing); base document plus a `translations` overlay (asymmetric, and repeater arrays drift between languages).

### 30.5 API behaviour

- Public endpoints accept `?locale=vi|en` (default `vi`) and return **flattened** strings for that locale. Slug lookups use `slug.<locale>`. Detail responses include `alternates`.
- The locale is part of the query string, so edge and in-process cache keys already separate languages.
- Admin endpoints return and accept the full `{ vi, en }` maps.
- Error `message` is English and for developers. Both frontends translate by error `code` (and validation issue code) from their dictionaries.
- Contact requests store the visitor's locale; notification and any auto-reply email follow it.

### 30.6 SEO

`<html lang>` per page; self-canonical per language; `hreflang` alternates for each locale the page exists in plus `x-default` → Vietnamese; `og:locale` and `og:locale:alternate`; sitemap entries for both languages with alternate links; JSON-LD `inLanguage`.

### 30.7 Formatting and fonts

Dates, numbers and relative times use `Intl` with the active locale. Fonts are subset to include Vietnamese diacritics.

### 30.8 Admin interface

The admin UI chrome is also available in Vietnamese and English, switched from its header and stored in `localStorage`. It needs no URL prefix because the admin is neither indexed nor server-rendered.

### 30.9 Adding a third language later

Add the code to `LOCALES`, add a dictionary file, add the language to code defaults, and add the per-locale slug indexes. Localized maps gain a key; no document restructuring is needed.

## 31. Analytics

Analytics is never a dependency of rendering or of any core flow. All calls go through one abstraction (`analytics.track(event, props)`), which is a no-op when nothing is configured or consent is absent.

| Item | Phase | Notes |
|---|---|---|
| Google Search Console (DNS verification, sitemap submission) | **MVP** | No script, no cookies. Essential for monitoring indexing. |
| Cookieless, privacy-friendly page analytics (hosted or self-hosted) | **MVP [Recommended]** | No cookie banner needed in most jurisdictions because no personal identifiers are stored. Loaded after idle. Provider and site id come from site settings. |
| Conversion event: `contact_submitted` (with service and source, no personal data) | **MVP** | The single business-critical metric. |
| Core Web Vitals field data (`web-vitals` → analytics endpoint) | Phase 2 | Validates the §21 targets with real users. |
| Google Analytics 4 / tag manager | Phase 2, only if marketing requires it | Sets cookies and transfers data to a third party, so it needs a consent mechanism. |
| Consent management banner | Phase 2, required **before** any cookie-setting or advertising tag | Tags stay blocked until consent; consent state stored locally. |
| UTM capture on contact requests | MVP | Stored in `contact_requests.meta.utm` to attribute leads without any tracking cookie. |
| Dashboards combining leads, traffic and content performance | Phase 2–3 | |

**Privacy implications.** The contact form collects personal data, so the privacy page must state purpose, retention and contact details, and the form needs an explicit acknowledgement. If the company targets clients in the EU, GDPR applies; Vietnam's personal-data protection rules also impose consent and notice obligations. These are legal questions: have counsel confirm the consent wording, retention period and whether the chosen analytics tool requires a banner. The architecture supports either answer because tags are consent-gated and the analytics provider is configuration.

Admin configures analytics by **provider + identifier** fields only. There is no free-form "paste a script" setting; that would be a stored-XSS feature.
